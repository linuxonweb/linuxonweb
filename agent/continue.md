### Guest stability finding: transient ENOMEM on process spawn (cause measured; mitigation opt-in)

Symptom: while running the jit-test slices about 1 in 160 process launches failed with "clone: Out of memory", "vfork: Out of memory" or "can't execute 'busybox': Out of memory" although the 4 GB guest had 3.78 GB free, MemAvailable stayed flat and the process count stayed at 50-54. A retry usually works. The same failure during Firefox startup would look like a crash or hang.

Cause (spawn/runs/log, page parameter spawndiag_log=1, 600 loops x 4 launches): 72 of 2400 launches failed and every failure is the host refusing a new per-process memory: "RangeError: WebAssembly.Memory(): could not allocate memory" (60 at exec, 22 + 19 at the fork copy), with guest MemFree unchanged at ~3.85 GB. Code path: exec -> kernel load_wasm_binary (arch/wasm/kernel/binfmt_wasm.c) -> host import compile_end -> allocate_shared_memory, any exception returned as -12; non-CLONE_VM clone -> child worker copies the parent memory into a new allocate_shared_memory, exception reported as -12 through user_copy_status (web/linux/dist/worker.js). allocate_shared_memory (wasm.js) first halves the maximum on failure, so some processes silently get a smaller maximum (9 "SPAWNDIAG degraded" lines in that run). Workers are recycled, and a recycled worker's isolate keeps the memories of processes it ran alive until it happens to collect garbage, so the browser's address-space budget for wasm memories fills with dead processes' memories.
