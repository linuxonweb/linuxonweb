# General Linux Vulkan/OpenGL support

Source-backed plan, 2026-10-04. This review made no GPU implementation changes and ran no builds or runtime tests. Follow the project order: current Firefox JIT acceptance, first Sites redeployment, general Linux GPU support, Firefox GPU acceptance, second Sites redeployment. Preserve home, clipboard, settings, application layout and rollback; build with musl, release settings without debug information, and the original optimizer.

## Existing evidence and reusable code

Retain the successful standalone benchmark in `/mnt/p6/project/build/nightly-current-native-vulkan-run-20261004/benchmark-summary.json`: the same native Linux/Wasm public-loader clear/fullscreen-triangle module through genuine Rust wgpu 30.0.1 passed independent CPU-reference pixels on BrowserWebGpu hardware and SwiftShader. It measured 44.0682 versus 1.22176 completed frames/s, a 36.0693 ratio. The measured interval includes submit/idle, transport and readback, and excludes guest pixel comparison; it is not display FPS or an isolated GPU timestamp. Genuine Rust Gl fallback also passed correctness, without a matched software acceleration comparison. This evidence remains valid for its pinned workload and bytes; it does not establish concurrent applications, swapchain presentation, OpenGL on the Rust service, Firefox GPU or release acceptance.

## Proposed common architecture and necessary gaps

Use Vulkan applications → guest ICD → general host service → Rust wgpu. Use OpenGL/GLES applications → shared Mesa EGL/Zink → that same ICD/service. Prefer actual BrowserWebGpu, with genuine Rust Gl/WebGL fallback only for its supported negotiated profile. Firefox consumes these interfaces as one application; its NSPR/static loading adapters remain separate from the general graphics executor.

User direction reaffirmed on 2026-10-04: ship the common guest graphics libraries and machine-owned host service for all Linux applications. Keep the public Vulkan/EGL/OpenGL entry points, backend selection, capability discovery and resource lifecycle independent of client names. Applications should use the installed libraries through their normal graphics APIs. Validate reusable interfaces with independent standalone and concurrent clients before integrating Firefox.

The shared host service/protocol belongs to the machine graphics subsystem, independently of Firefox or any window. Each authenticated guest address space, session, Vulkan device and EGL context needs isolated typed resources, generations, quotas and submission ownership. Client exit drains and releases only its resources; service/device loss invalidates affected generations and cancels waiters. Evaluate shared adapter/device pooling against per-client devices for isolation, supported limits and measured cost; a single shared GPU device is not an acceptance requirement.

Existing shared transport uses per-session Rust devices: `guest-gpu-vk.js:166–174` creates a renderer per session, `bridge.mjs:11` calls `Renderer.create`, and Rust `lib.rs:217` requests a device. Rust `close()` destroys that device (`:984–995`). This can be a valid initial general architecture once ownership, lifecycle, negotiated capabilities and presentation are correct. Extract reviewed service assets from test/candidate import paths; if device pooling is adopted, separate pooled device lifetime from client cleanup.

Required ownership work is concrete: `guest-gpu-vk.js:201` receives no trusted caller identity, and CALL/CLOSE retrieve globally numbered sessions (`:208,215`). Owner detach only removes the thread attachment (`guest-gpu-owner.js:439`). Bind admission/access/cleanup to trusted address-space generations, preserve shared process resources on thread exit, and specify exec/fork/loss behavior. Within an application, `icd.c:45,188` permits one live instance; Zink caches the last instance/GDPA (`zink_static_vk.c:55–56,83–101`). Add correct multi-instance/device routing and thread-safe recording/queue ordering.

Capabilities must intersect actual host adapter/device features, limits and downlevel behavior with implemented guest ABI/translations and tested emulations. Replace substring HELLO parsing (`icd.c:151`) and fixed profiles (`host.mjs:194–200`) with a versioned typed reply containing actual backend/software identity and separate Vulkan, GL/GLES and native-wgpu profiles. Mesa may expose only the GL/GLES level supported by that intersection. Unsupported requests fail explicitly; version strings are not conformance evidence.

Rust selects BrowserWebGpu or Gl (`lib.rs:191–205`), requests empty features and downlevel defaults (`:210–221`), and refuses browser force-fallback requests (`:186`). Its current rendering uses nonindexed, one-instance draws (`:890`); guest Zink has limited indexed gathering/emulation. Rust compute is absent, and the external graphics path refuses compute (`host.mjs:127,191`). Extend only required resource/shader/queue semantics with meaningful tests; do not silently reuse JavaScript compute as Rust execution. Audit Zink's no-op line width/blend constants (`zink.inc:846,850`) before exposing those states.

WSI is unfinished: both `wsi_acquire` and `wsi_queue_present` return `VK_ERROR_FEATURE_NOT_PRESENT` (`wsi.inc:221–240`). Implement acquire/release states, completion synchronization, timeout/error behavior, resize/loss and pacing. Initial readback/XPutImage presentation is reasonable; existing readback cube/gears applications do not prove swapchain presentation. Mesa currently disables GLX and window platforms (`configure-wasm32.sh:22`); implement genuine EGL/X11 window or GLX support when the application requires it. Replace the surfaceless selection workaround that forces software/CPU identity (`zink-egl-static.c:71–73`, `icd.c:261–272`) with honest discovery.

## Implementation contracts for reusable clients

Package the public Vulkan loader/ICD and shared Mesa `libEGL`, `libGL`/`libGLES` entry points for the guest's supported musl application ABI. Verify normal loader discovery, library resolution and proc-address dispatch with independently compiled clients, including the existing static-loader route where required by Linux/Wasm. A Firefox-only preload, special application name or copied renderer does not establish general library support. GLX is a separate interface for clients that use it; surfaceless EGL gears cannot establish GLX or EGL window-surface support. Keep production service, translators and pinned Rust Wasm assets in a common graphics package, with test harnesses importing that package rather than production importing test/candidate files.

Keep guest API compatibility and host execution profiles explicit. The current host render-command protocol is a bounded translation profile, not a complete Vulkan implementation or native wgpu HAL. Every exposed Vulkan feature/extension, GL/GLES context version and native-wgpu operation needs supported translation or tested emulation. The negotiated reply should include protocol/profile versions, operations, formats/usages, actual device limits, presentation routes, backend identity and fallback reason. Reject incompatible peers and unavailable context/device requests.

Zink compatibility is conditional: upstream lists baseline requirements including `logicOp`, `fillModeNonSolid`, `alphaToOne`, `shaderClipDistance`, maintenance/renderpass/framebuffer/timeline extensions and custom border colors, and provides a requirements checker. Check the exact pinned Mesa profile and its real behavior against this ICD before accepting any GL level; suppressing warnings or announcing an extension is insufficient. The bounded Rust bridge does not automatically satisfy that profile. [Mesa Zink requirements](https://docs.mesa3d.org/drivers/zink.html).

Likewise, negotiate actual wgpu downlevel flags and formats as well as numeric limits. wgpu 30.0.1 documents that WebGL2 lacks compute and indirect execution, and its WebGL2 default limits have zero storage-buffer/storage-texture slots. Genuine Rust Gl fallback therefore serves only validated supported workloads, with explicit refusal of unsupported operations; it cannot inherit the BrowserWebGpu feature set. [wgpu downlevel flags](https://docs.rs/wgpu/30.0.1/wgpu/struct.DownlevelFlags.html), [wgpu limits](https://docs.rs/wgpu/30.0.1/wgpu/struct.Limits.html).

| Boundary | Required lifecycle contract |
|---|---|
| Machine → guest address space | Trusted transport supplies machine and address-space generation identities; guest-provided session numbers alone never grant access. Threads may share their address space's API resources under API synchronization rules. |
| Address space → API device/context | OPEN/CALL/CLOSE bind to that owner. Handles include kind and generation; foreign, freed and reused handles fail. Multiple Vulkan instances/devices and EGL contexts route independently. |
| Submission → completion | Preserve queue order, resource visibility and actual completion semantics. Retain submitted resources until safe to destroy; readback, fences, map callbacks and presentation cannot signal prematurely. |
| Thread exit / abandoned call | Detach cancels that thread's pending writes without destroying another thread's shared device. If asynchronous OPEN finishes after its caller disappears, release the orphan session/device. |
| Process exit / exec / fork | Last owner exit or exec revokes its generation, cancels waiters and releases only its resources. Define supported fork behavior explicitly; copied handles cannot acquire unrelated ownership. |
| Service/device loss | Invalidate affected generations and report API loss/error results. Reconnection creates fresh handles. Per-client devices should contain client loss; pooled-device loss may affect every client using that device. |

The existing owner checks completion before writing guest memory, which is reusable, but `openSession()` allocates before that completion check. Cleanup must cover that race as well as ordinary CLOSE. Bound per-client resources/outstanding work and aggregate machine consumption; schedule independent clients so a stalled client cannot indefinitely block a survivor. Keep global device shutdown distinct from client teardown.

Presentation belongs to the shared graphics/window subsystem. Bind each surface to its owning device and guest X11 window generation; reject another client's window or a reused XID. Implement image transitions from available to acquired to queued to available, with acquire signals, present waits, per-swapchain results, timeouts and recreation after resize/loss. Readback/XPutImage can be the first implementation, recording its CPU transfer cost. EGL window swaps and GLX swaps must use that same presentation/lifetime contract. Direct host-canvas presentation or zero-copy sharing remain future routes until implemented and accepted.

## Acceptance sequence after JIT and the first deployment

1. Preserve the existing benchmark and exact accepted bytes. After service changes, rerun the affected public-loader clear/triangle correctness and teardown checks against the reviewed service; identify actual Rust backend and served assets.
2. Validate a separate textured Vulkan client and genuine Rust compute if supported. Run two independent Vulkan processes concurrently; verify distinct pixels/resources, then close or terminate one owned client and prove the survivor still renders. Exercise relevant stale/cross-client rejection, quotas, thread/process teardown and device loss, with owned-resource counts returning to zero.
3. Validate actual swapchain vkcube when WSI exists, including resize, multiple windows and repeated launch/close. Keep headless/readback and presentation acceptance distinct.
4. Validate shared Mesa EGL/OpenGL with gears plus a separate textured application on the Rust service. Run OpenGL+OpenGL and Vulkan+OpenGL concurrently through the same ICD/service; verify isolation, survivor rendering and teardown. Add an actual GLX application once GLX exists. Test fallback correctness for supported workloads and explicit refusal otherwise.
5. Measure acceleration for the accepted standalone and concurrent application workloads using matched hardware/software binaries, sizes, readback/presentation paths, warmups and deadlines. Retain all measured frames and actual adapter identity. The existing clear/triangle acceleration result remains established for its scope; new app/API acceleration needs its own comparison.
6. Exercise the intended guest-native wgpu HAL in a standalone Rust application, then validate Firefox WebRender, WebGL1, WebGL2 and WebGPU separately. Firefox's current GL probe explicitly performs no context test (`glxtest-egl.c:69`), and the native backend patch excludes Vulkan on wasm32 Linux musl (`tools/nightly-musl/patches/nightly-wgpu-core-native-backend-cfg.patch:11`); those integration gaps need implementation, not preferences. Capture actual compositor/GL/backend identity and API pixels/results, map/error/loss behavior and process restart. Keep codec use Unknown without independent proof.

For each accepted standalone/concurrent arm, retain client binary and served-library/service hashes, loader/proc-address route, negotiated API/profile and backend/fallback identity, independent output checks, measured frame intervals/timing boundary, completion/cleanup counts, exit status and owner receipt. Concurrent checks must prove overlapping execution through the same machine service and independent outputs/windows; sequential launches or isolated harness services do not establish that gate. Use matched hardware/software arms for each accepted Vulkan and OpenGL workload before Firefox integration. Report rendering, readback and presentation timings separately where measured. Correctness, acceleration, concurrent ownership and window presentation each have their own pass status; an unsupported API cannot inherit another API's pass.

Run checks appropriate to the affected changes; do not require unrelated full JIT/TLS suites after every GPU iteration. For each runtime job, use task-owned disk scratch/caches under `/mnt/p6/build`, explicit resource/deadline bounds, and freshly measured matching host/browser/guest CPU counts. Before the final release, run the applicable package/release checks, deploy through Sites with rollback and an in-page update choice, and preserve user state. Prepared code and this plan are not runtime acceptance.
