# P1: host GPU per-frame overhead (2026-10-01)

The V2 profile (`docs/vkgears-v2-profile-20261001.md`) showed that the WebGPU
renderer's `checked()` cost about 1.27 ms of a 5.23 ms vkgears nopresent frame,
and 3.7 ms of 16.8 ms with presentation. Each checked op pushed 3 error scopes
and then awaited 3 pops serially. Each pass awaited them twice (encode, then
submit). Each readback also created and destroyed a staging buffer.

This packet removes most of that overhead without weakening the error
semantics:
- vkgears on NVIDIA WebGPU is 24-31% faster in all four configurations.
- All 20 guest Vulkan suites pass with identical check counts on NVIDIA WebGPU
  and Intel WebGL2.

Change commit: `f08df1e` (base `d66ae18`). Only
`web/linux/tests/guest-vulkan-graphics/renderer.mjs` changed. The four
`storage.py` guards also accept the new task root.

Evidence:
- `docs/evidence/gpu-host-p1-20261001.json`
- raw runs in `/mnt/p6/build/gpu-host-p1-20261001`

## Design

From the options in the packet, this change combines (a), (b) and (c); (d) is
not needed.

1. **Scopes popped at once, awaited together (option a).**
   - WebGPU assigns an error to a scope at the moment of the native call.
   - So `scoped(action)` pushes the three scopes, runs the call synchronously,
     and pops right away. It returns the pop promises without awaiting them.
   - A pass encodes in one scope set and submits plus `onSubmittedWorkDone` in a
     second. The pass then awaits both sets and the work-done promise in a
     single `Promise.all`: one GPU-process round trip instead of three.
   - A readback works the same way: encode, then submit plus `mapAsync`, then
     one combined settle.
   - Classification is unchanged: the first scoped error in pop order wins
     (validation -22, out-of-memory -12, internal -5), then any thrown error.
   - A rejected work-done or `mapAsync` promise is captured separately, so the
     scope errors are still classified first, as before.
2. **Deferred upload scopes (option b).**
   - Vertex, uniform and texture uploads are queue writes whose range,
     alignment and handle were already validated in JavaScript.
   - The upload returns as soon as its scope set has been popped. The pops go
     into `deferred`.
   - Every later awaited operation (pass, readback, create, ...) awaits the
     deferred pops in the same `Promise.all` as its own.
   - At most 32 may pend before a forced settle.
   - A synchronous throw from the write is still classified immediately.
3. **Persistent readback staging (option c).**
   - One `MAP_READ` buffer of the exact readback size is reused.
   - While in use it is a tracked native object that counts against the byte
     budget, exactly like the old per-readback buffer. The budget check before
     it is unchanged.
   - While idle (only if it is ≤1 MiB, and only while the renderer is open) it
     is held outside the budget.
   - A different size, close, loss or failure destroys it, and
     `buffersDestroyed` is counted then. Created/destroyed counters still
     balance at close.
4. **No `uncapturederror` backstop (option d).**
   - Every native call is still inside a scope, so no error escapes to it.
   - Device loss already ends the renderer through the existing
     `device.lost`/`wait()` path.

### WebGL2 renderer: not changed

The WebGL renderer (`guest-vulkan-webgl/renderer.mjs`) has no error scopes. It
calls `gl.getError()` once after each upload or pass. That is one synchronous
query, not three serial async round trips, so there is no analogous saving
there.

Its per-pass cost is the fence poll: `clientWaitSync(…, 0)` plus
`setTimeout(poll, 4)`, so each pass waits at least about 4 ms. Changing that
alters busy-wait and CPU-use behaviour, so it is out of scope here and listed
as a follow-up.

## Error semantics

| Case | Before | After |
|---|---|---|
| JS validation/budget before execution (bad range, budget, stale handle) | -22 / -12, recoverable | identical (code paths unchanged) |
| Encode-time native validation error in a pass | -22, attachments keep prior state | -22, attachments restored to prior state. The invalid command buffer makes the submit a no-op validation error with no effects (verified) |
| Native error at submit/work-done (after possible effects) | classified from scope; initialized=false | identical, in the same order |
| Readback encode/map error | -22/-12/-5, buffer released | identical; staging is released, not cached |
| Native error from a queue write (upload) | reported on the upload as -22/-12 | upload is acknowledged (0); the next awaited op fails with **terminal -5**, renderer state `failed` |
| Device loss | -19 on the next op, state `lost` | identical |
| Error from an upload deferred past `close()` | n/a | not reported (renderer already closed) |

The one deliberate difference is the upload row. JavaScript pre-validation
already rejects bad range, alignment and handles, so a native queue-write
error can only come from out-of-memory, an internal error or device loss. It
cannot come from a guest mistake.

Once the guest has been acknowledged, the write cannot be failed
retroactively. Treating it as terminal (-5 after possible effects) is
therefore the conservative reading. host.mjs already ends the session on -5.
This never turns a recoverable error into silent success, and never lets a
partially written buffer be used without the session failing.

The semantics gate is `semantics-run1`. It drives the old (`d66ae18`) and new
renderers side by side on the real NVIDIA device and injects native errors by
wrapping one device or queue call. Results:
- **Identical step-by-step:** encode error, submit error after effects,
  readback encode error, upload pre-validation, and device loss. "Identical"
  covers status codes, renderer state and pixels.
- **Different, as designed:** in the upload native-error case the old renderer
  returns -22 and continues; the new one returns 0, then -5 with state
  `failed`, then -19.
- **Counters:** every case ends with nativeObjects=0, allocatedBytes=0 and
  balanced buffer/texture counters.
- **Runner:** no page exceptions and no console errors.

## FPS before/after: vkgears on NVIDIA WebGPU

Setup:
- Page: `?gputest=1&gputestapp=vkgears&vkmode=MODE&gpubackend=webgpu[&vksize=128x128]`.
- Browser: headful `DISPLAY=:0` Chromium with Vulkan Dawn. The adapter is
  `{vendor:nvidia, architecture:maxwell}` in every run.
- Measurement: 50 s observed after the first `VKGEARS_FPS` line. The value is
  the median of the 5 s intervals, excluding the first.
- Repeats: two per phase. "Before" used the unmodified worktree first. Mean of
  the two medians is shown.

| Config (render size) | Before r1 / r2 | After r1 / r2 | Before → After | Frame ms saved |
|---|---|---|---|---|
| nopresent, default 300x300 (render 128) | 185.22 / 185.25 | 240.09 / 238.93 | 185.2 → 239.5 (+29.3%) | 5.40 → 4.18 (1.22) |
| nopresent, 128x128 | 185.39 / 189.38 | 233.54 / 231.98 | 187.4 → 232.8 (+24.2%) | 5.34 → 4.30 (1.04) |
| present, default 300x300 | 56.21 / 51.88 | 69.69 / 72.13 | 54.0 → 70.9 (+31.2%) | 18.50 → 14.10 (4.40) |
| present, 128x128 | 63.04 / 64.44 | 80.59 / 77.91 | 63.7 → 79.3 (+24.3%) | 15.69 → 12.62 (3.07) |

Notes on the table:
- **Load average.** The 1-minute load average, median per run, was 1.4-3.5
  before and 1.2-4.4 after. The B2c agent was running concurrently.
- **Unstable intervals.** The nopresent 128x128 after-runs had single unstable
  intervals (max 401 and 341 FPS). Their medians are stable.
- **Agreement with the profile.** The nopresent saving (1.0-1.2 ms) matches
  the 1.27 ms of scope cost from V2. The present saving (3.1-4.4 ms) matches
  V2's 3.7 ms: the readback's scopes plus the per-frame staging
  create/destroy.

Host-only microbenchmark: the renderer driven directly in the page, median of
3 rounds of 300 frames. Each frame does a 63,360 B vertex upload, a 256 B
uniform upload and a clear pass, plus a 128x128 readback in present mode.

| | Old | New |
|---|---|---|
| nopresent | 2.72 ms/frame | 1.22 ms/frame |
| present (128x128 readback) | 5.52 ms/frame | 1.77 ms/frame |

Staging buffers created per 330 present frames dropped from 332 to 3.

## Failed or irregular runs kept

- **`fps-before-nopresent-{default,128}-r1`: runner `pass=false`.**
  - The first version of the runner's nvidia check matched `VK_DEVICE_NAME`,
    which is the ICD's own name.
  - The page logs show `backend=webgpu adapter={"vendor":"nvidia","architecture":"maxwell"}`.
    The FPS data is valid and is used above.
  - The check was fixed to read the host adapter line for all later runs.
- **`fps-after-present-default-r2`: dev server did not exit within 5 s of
  SIGTERM.**
  - The result was written with server exit `null`.
  - The owned child (verified PPID) was SIGKILLed by hand. Its measurement is
    complete and valid.

## Follow-ups (not done)

- **WebGL2 fence polling.** Each pass waits at least 4 ms on the
  `setTimeout(4)` poll. Candidates are a MessageChannel-paced poll with a
  bounded spin budget, or skipping the per-pass fence when no readback
  follows.
- **Earlier pass replies.** Replying to a pass before `onSubmittedWorkDone`,
  and folding its completion into the next op, would save one more round trip
  per frame. It needs the same terminal-on-late-error argument as uploads.
- **Guest/ICD side (V2 ranking).** Static vertex data is re-uploaded every
  frame, and the 128→300 upscale plus XPutImage cost about 4 ms.
