## Outcome

The guest Vulkan ICD, built with `-DGUEST_VK_ZINK=1`, now passes Zink's device
and layout initialization. Inside the real guest, `zink_create_screen()` returns a
screen on both WebGPU (NVIDIA MX110) and WebGL2 (Intel ANGLE).

EGL still fails with `EGL_NOT_INITIALIZED`. The root cause is now pinned (see
Gate B): the ICD exposes no B8G8R8A8 color format, so the kopper/surfaceless
DRI frontend builds zero framebuffer configs. Adding that format is the next
packet. It is not a one-line change, because the format has to be supported
through attachments, copies and readback on both backends.

All 20 regression suites pass with the final sources (`all-run2`).

## Real vs. bounded/stubbed

These are real, implemented semantics with pixel and readback checks:

- renderpass2: 1 subpass, 1-2 attachments, at most 2 dependencies. There is no
  NextSubpass2.
- Dynamic rendering: 1 RGBA8 color attachment plus an optional D32/D16 depth
  attachment, over the full render area. A NULL renderPass requires
  VkPipelineRenderingCreateInfo.
- Descriptor update templates: DESCRIPTOR_SET type only, at most 4 entries,
  UBO or COMBINED_IMAGE_SAMPLER, count 1.
- Timeline semaphores:
  - counter value, host signal (must increase), and submit-time
    wait/signal values;
  - vkWaitSemaphores supports WAIT_ANY. It is **non-blocking**: a value not
    yet reached returns VK_TIMEOUT, because submissions complete synchronously.
    Blocking waits are B2b.
- nullDescriptor: a null UBO (offset 0, WHOLE_SIZE) binds a lazily created 16 KiB
  zero host UBO.
- maintenance5: vkGetRenderingAreaGranularityKHR only (1x1).

The following are bounded, emulated or not implemented:

- Push constants: 128 bytes are advertised and layouts record their ranges.
  vkCmdPushConstants and shader push-constant blocks are **not implemented**
  (B2c), so a pipeline that reads them fails at creation or translation.
- Null sampler or image descriptors are not handled.
- No dynamic state beyond what A1-A6 already had.
- Formats:
  - R8G8B8A8_UNORM (optimal features 0xd081);
  - D32_SFLOAT and D16_UNORM (0x200);
  - R32G32[B32[A32]]_SFLOAT as vertex buffers only (0x40);
  - **no** B8G8R8A8, Z24 or stencil formats.
- maxImageDimension1D, 3D and Cube are 0. maxColorAttachments is 1.
  maxMemoryAllocationSize is 1 MiB, and image size is at most 128x128.
- Base Zink requirements that are still missing (Mesa warns but continues):
  logicOp, scalarBlockLayout, EXT_custom_border_color, EXT_line_rasterization.

Root cause of the EGL failure, as read from the Mesa 26.2.3 sources:

1. `dri_fill_in_modes()` (`src/gallium/frontends/dri/dri_screen.c`) drops
   RGBA-ordered formats unless `dri_loader_get_cap(DRI_LOADER_CAP_RGBA_ORDERING)`
   is true.
2. That cap is only queried through `screen->image.loader`. The surfaceless
   platform answers it with 1 for the image loader. However, its
   `kopper_loader_extensions` (used for zink + `LIBGL_ALWAYS_SOFTWARE`) contain
   no image loader, so the cap reads 0.
3. Only RGBA8 is renderable and no BGRA format is, so zero configs are created.
   `driCreateNewScreen3` then returns NULL, which produces "failed to create
   dri2 screen".

The fix is not a Mesa patch. The ICD has to support VK_FORMAT_B8G8R8A8_UNORM.

## Next packet: B2a-2

1. **B8G8R8A8_UNORM as a color attachment, sampled image and transfer format.**
   - Store it on the host as an RGBA texture holding the logical channels, so
     shaders, clears and blending are unchanged.
   - Swap the R and B bytes only at the guest memory boundaries: buffer-to-image
     uploads, image-to-buffer readback, and RGBA<->BGRA image copies and blits.
   - Touches roughly 10 format checks in `icd.c`, `graphics.inc`,
     `graphics-commands.inc`, `transfer.inc`, `zink.inc` and `wsi.inc`.
   - On WebGPU, `bgra8unorm` could be used natively instead.
2. **maxImageDimension1D** is 0, so Zink computes `max_texture_2d_size =
   MIN3(dim1D, dim2D, 16384) = 0`. That gives GL MaxTextureSize 0, the next
   probable failure once configs exist. Advertise 128 in Zink builds, or support
   1D images as 2D with height 1.
3. **Push constants (B2c).** Zink's gfx layout always has a 52-byte push range,
   and its shaders read it (draw id and similar), so the first draw needs
   vkCmdPushConstants plus translator support, for example by emulating the
   block as a UBO.
4. **Stencil/Z24 formats.** Optional, because the configs work with Z16/Z32F
   and no stencil.
5. **Base requirements Mesa warns about:** logicOp, scalarBlockLayout,
   EXT_custom_border_color, EXT_line_rasterization.
6. **Blocking timeline waits (B2b).** The 1 MiB maxMemoryAllocationSize is also
   below Zink's typical buffer slabs; expect allocation failures after context
   creation.
